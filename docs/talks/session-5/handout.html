§2Rung 0 — the channel becomes the record

5 minutes · no code · no Agentforce · no licence
You get: a Slack channel that is a CRM record — 86 live fields, editable in place, with the object badge next to the channel name.

This is the highest value-per-minute thing in the whole talk, and most people don't know it exists. It ships in every paid Slack workspace, switched off.

Salesforce Setup  →  search "Slack"  →  Slack Channels for Records
  → enable it for ONE object (start with Opportunity)
Then, on any record:  Slack panel  →  Create a channel
It bites here. Every record tab renders empty until someone clicks the sync icon, and each takes 20–30 seconds. If you demo this cold, your audience sees four blank tabs. Open all of them and sync before anyone is watching.
There is no metadata type for it. You cannot deploy it, script it, or package it. A human clicks it in every org, and again after every sandbox refresh. Put it on your post-refresh checklist now.
What to notice: the padlocks on the tab columns. Editable fields have none; the ones your profile can't write show a lock. Slack is rendering your field-level security.

§3Rung 1 — an agent that answers, and asks before it writes

an afternoon · configuration only · still no code
You get: an agent in that channel answering from real fields, and refusing to change one without a human yes.

The three things an agent is

  • The agent — configuration in your org. Not an app you install, not a prompt in a box.
  • A topic — one job. Its description tells the planner when to pick it.
  • Actions — the only verbs it owns. Ours has seven and no more.

The seven actions

Identify Record by Name          Get Record Details
Query Records                    Extract Fields and Values from User Input
Update Record            ← isConfirmationRequired = true
Send Message to a Slack Channel  Reply in Thread
The gate is a property, not a prompt. isConfirmationRequired sits on the action. No instruction removes it, and no user phrasing talks past it. That is the difference between a guardrail and a polite request.

The instruction that mattered most

The agent kept drafting stage values that don't exist. Nine careful rewrites didn't fix it. Pasting the 29 real values into one instruction did.

SELECT MasterLabel FROM OpportunityStage WHERE IsActive = true ORDER BY SortOrder

Give agents data, not adjectives. And note: OpportunityStage is a standard queryable object, so the agent could fetch that list itself with an action it already has. Pasting is the cheap fix; querying is the right one. Pick knowingly.

Only one agent type reaches Slack. It must be an Employee Agent. A Service Agent won't install, and an Agent Script (.agent / aiAuthoringBundle) agent can't be deployed to Slack at all — those carry agentDSLEnabled = true and Slack only takes the template lane. I lost most of a day to this.
The label must contain the word "Agent." Salesforce's own docs say so in passing. Get it wrong and the agent is silently invisible in Slack's review queue.
Test your own org early. In my sandbox a brand-new agent never reached Slack's review queue at all — only agents whose Slack registration came over in the clone from production would install. I could not find that documented anywhere. Don't assume it works until you have installed one.

MIT licensed, ~1,300 lines, three pip dependencies, no database. State lives in a Slack List — a spreadsheet inside Slack that you and the worker can both read. That choice is most of why it's small.

JobTriggerWhat it does
Answeran @mentionreplies in-thread, grounded in the List

Socket Mode is why this is easy. The worker dials out to Slack. No public URL, no ingress, no TLS to manage. It runs the same on your laptop and on a hosted tier.
Socket Mode does not replay missed events. If the process is restarting when a mention arrives, that mention is gone — no error, no retry, no log. Every deploy is a small hole in your coverage. Don't deploy during a demo.
A List created by an app is shared with nobody. Not even you. Call slackLists.access.set with access_level to grant it, and note there is no getter — verify via files.info and read the channels field. I shipped a button that gave everyone "access denied" because of this.

§5Rung 3 — two agents, one channel

an hour, once rungs 1 and 2 are standing
You get: an Agentforce agent handing work to your worker, and a very instructive failure when you try it the other way.

Agentforce → your worker: works

Give the agent a Send Message to a Slack Channel action, and put your worker's Slack handle in the instruction so the agent writes the mention itself:

…end by mentioning the onboarding worker using exactly this handle,
character for character: <@YOUR_WORKER_USER_ID>
Don't let the human type that handle. If your instruction to the agent names the worker, the worker wakes on your message — before the agent has done anything — and answers a question nobody asked. Put the handle in the agent's config, not in the human's sentence.
A conversational reply is invisible to other bots. Agentforce replies in Slack are ephemeral to whoever asked; the channel sees only "I've privately shared an answer with @you." Only the explicit Send Message action produces a real message another bot can hear. Say "post to this channel" in your ask, or nothing fires.
app_mention is intermittent for bot-authored mentions. Once it didn't fire at all; next time both it and the message listener fired, producing two replies 0.6 s apart. Listen on both and dedupe on (channel, event ts). Don't "fix" it by deleting a listener.

Your worker → Agentforce: fails, and this is the lesson

Have the worker tag the agent and ask for a stage change. The agent wakes in about 20 seconds and says:

"Please reach out to your Slack Administrator to get access."

Agentforce in Slack binds every session to the invoking user's Salesforce identity. A bot has no Slack-to-Salesforce user mapping, so there is no session to open. Two agents can reach each other through the channel and still cannot move a CRM record between them.

You can fix it. Here is the bill.

RouteHowWhat it costs
Client credentialsExternal Client App, a Run As user with API Only, Agent API with bypassUser: trueEvery write becomes one service account. No user attribution, ever.
JWT, named userPrivate key, "issue JWT-based access tokens for named users", bypassUser: falseReal attribution — and you now hold a key that can act as any human in the org.
Keep the humanOne extra messageOne extra message.

And before either: an Employee Agent cannot be called by the Agent API at all. You'd rebuild it as a Service Agent — which is assigned its own Einstein Agent user. Both routes begin by giving the agent an identity.

The Agent API parameter that chooses between these is literally called bypassUser. Salesforce named it honestly. Read that name before you set it.

§6Make it yours

The demo is a staffing deal. Almost none of that is load-bearing. Here is what to swap.

SwapWhereNotes
The objectSetup → Slack Channels for RecordsAny object. Case, Job, Project, Order. The tabs come free.
The processseed/onboarding.csvThe List is one row per step. Rename the columns and the worker follows — every Lists call goes through one adapter, tools/lists.py.
The agent's jobthe topic's instructionsNine plain-English rules. Start by pasting your picklist values in.
The verbsthe action listTen per subagent is the cap. Add nothing you would not want it to do unattended.
The modelANTHROPIC_MODELagent.py is 42 lines precisely so the provider is swappable.
The clockCHASE_CRON_HOUR, TZA container runs UTC unless you set TZ. This has caught me.
Who it can wakeHANDOFF_BOT_IDSAllow-list the agents that may hand it work. Empty means any bot.
Who it hands toAGENTFORCE_USER_IDUnset and it just states its limits. Set and it names the agent that can act.
The one design decision worth stealing: the worker owns a Slack List and never writes to Salesforce; the agent owns Salesforce and never writes to the List. Neither can corrupt the other's system, and every number on screen is countable by eye. That split cost nothing and removed a whole class of bug.

§7Dead ends — the week you don't have to repeat

Building the agent in Agent Script

Slack-deployable agents carry agentTemplate = Slack__SlackEmployeeHelp and agentDSLEnabled = false. An Agent Script agent cannot be deployed to Slack. I built one, tested it to 33/33, and it could never appear. Use the template lane for anything Slack-facing.

A local action without schemas

A localAction missing input/schema.json and output/schema.json deploys and activates cleanly, and then silently cannot resolve. Nothing warns you. Only a metadata retrieve reveals it.

A bridge bot to give the worker an identity

We designed one, and rejected it. It would have made the demo smoother and the claim false. A guardrail you configure can be reconfigured; a credential that was never issued cannot be misused.

Trusting the admin panels

Slack's admin console showed 0 active agents while the agent was answering in a channel. Salesforce showed Connections: Needs Setup at the same time. Both were wrong. Behaviour is truth; panels are decoration.

Trusting a quiet log, or a green deploy

A green deploy means your deploy passed. It does not mean the thing works. Retrieve the bundle and read what the org actually stored — twice this session that is the only thing that found the bug.
